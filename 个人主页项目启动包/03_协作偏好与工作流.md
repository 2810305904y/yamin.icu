# 协作偏好与工作流

整理日期：2026-06-01

## 用户输入习惯

用户经常使用语音输入，所以文字里可能出现：

- 错别字。
- 同音词。
- 标点不稳定。
- 句子很长。
- 中途修正自己的想法。

协作时应优先理解意图，不要抓字面错误。只有在影响操作或可能导致错误配置时才追问。

## 用户喜欢的协作方式

用户不是代码背景，但愿意思考产品逻辑、成本、长期维护和用户体验。

更适合的沟通方式：

- 先讲“为什么要这么做”。
- 再讲“具体要点哪里、填什么”。
- 避免一次性倒太多术语。
- 对 Vercel、Resend、DNS、Git 等概念，用现实类比解释。
- 重要操作前说清影响范围。
- 做完后总结：改了什么、验证了什么、还有什么风险。

## 用户经常关心的问题

- 这个成本为什么这么算。
- 有没有更便宜的办法。
- 这个方案长期会不会难维护。
- 如果以后复制到其他项目，会不会又要补很多补丁。
- 是否会影响已经跑通的项目。
- 有没有必要做两个版本，还是应该统一成一个平台。
- 哪些东西需要记录、备份、写文档。

## 工作流偏好

用户偏好“先讨论逻辑，再动手”的模式，尤其是涉及架构、域名、邮件、部署、长期维护的时候。

推荐工作流：

1. 先确认目标和约束。
2. 用简单语言列出方案。
3. 给出推荐方案和理由。
4. 用户确认后再改代码或配置。
5. 改完后运行测试。
6. 推送到 GitHub。
7. 等 Vercel 部署。
8. 用户用手机或真实场景测试。
9. 根据截图和反馈继续修。
10. 稳定后写进度文档和备份说明。

## 版本命名偏好

用户对版本号的理解：

- `V1.5`、`V1.6`、`V1.7` 表示比较明显的新功能阶段。
- `V1.51`、`V1.52` 表示某个阶段之后的小更新。
- 如果小更新很多，也可以最终进入下一个大阶段，例如 `V1.6`。

实际协作中，曾经讨论过 `V1.511`，但用户觉得有点怪，最后倾向于直接进入 `V1.6`。

后续新项目建议在一开始写清版本规则，避免混乱。

## 文档与备份偏好

用户很重视后续能不能找回当时的判断。

稳定版本建议同时保留：

- 项目进度文档。
- 备份说明。
- 代码压缩包或 Git 提交。
- 关键配置说明。
- 如果涉及域名、Resend、Vercel，要写清楚环境变量和 DNS 逻辑。

不要把项目历史、当天做过什么、临时试错过程写进长期入口文件 `AGENTS.md` 或 `Memory.md`。

## 技术执行偏好

如果是网页项目：

- 改代码前先看现有结构。
- 尽量沿用已有风格。
- 推送前运行测试和检查。
- 不把素材库、文案库、备份资料混进网页代码仓库。
- 用户有时会用手机测试真实效果，手机截图比模拟器更有价值。

## 解释风格

用户喜欢能“把复杂东西变成能理解的形状”的解释。

有效表达：

```txt
能丢的东西 -> 放玩具域名
不能丢的东西 -> 放长期域名
```

```txt
Resend 不是创建一个真的邮箱，而是验证一个你拥有的发信域名。
验证通过后，可以从这个域名下的任意地址发信。
```

避免表达：

```txt
请自行配置 SPF/DKIM/DMARC 并检查 propagation。
```

应改成：

```txt
Resend 会给你几条 DNS 记录。你把它们填到域名平台里，它就知道“这个域名确实归你管”，之后才允许你用它发邮件。
```
