# 个人主页内容编辑工具需求草稿

文档版本：草稿 V0.1  
整理日期：2026-06-01

## 当前需求

个人主页不能只是一次性写死的展示页面。它还需要一个简单的编辑工具，让用户可以比较低成本地更新网站内容。

可以理解为：

```txt
公开主页 -> 给访客看
后台编辑页 -> 给自己改内容
```

后台编辑页可以是一个固定网址，例如：

```txt
/admin
/studio
/edit
```

最终路径待定，不应在公开页面上明显展示入口。

## 需要编辑的内容

### 项目区

需要能编辑：

- 项目名称。
- 项目说明。
- 项目状态，例如：已上线、建设中、计划中、先空着。
- 项目链接。
- 展示顺序。
- 是否显示。

可选增强：

- 项目图标。
- 项目卡片类型，例如大卡片、横向卡片。
- 备注文案。

### 正在进行 / 待办区

需要能：

- 新增待办。
- 删除待办。
- 修改待办文字。
- 修改状态色或进度。
- 调整排序。
- 标记是否显示。

### 奇怪念头区

需要能：

- 新增词条。
- 删除词条。
- 修改词条。
- 调整是否显示。

可选增强：

- 自动随机展示。
- 给词条设置颜色。
- 给词条设置权重，常出现或少出现。

### 自媒体与视频账号

需要能：

- 新增链接。
- 删除链接。
- 修改名称。
- 修改链接地址。
- 调整排序。
- 设置是否显示。

## 后台界面方向

后台界面可以和当前主页示意图保持相似结构，但加入编辑按钮。

基本思路：

- 仍然是四分区。
- 每个分区右上角有新增按钮。
- 每条内容或每张卡片有编辑、删除、上移、下移按钮。
- 修改时可以弹出小窗口或侧边面板。
- 保存后公开主页同步更新。

界面不需要做成复杂 CMS。目标是“用户自己能改”，不是做一个通用内容平台。

## 账号与权限

后台需要有保护，不应任何人都能打开修改。

可选方案：

### 方案 A：本地文件编辑

内容放在代码里的数据文件，例如：

```txt
projects.ts
todos.ts
thoughts.ts
channels.ts
```

优点：

- 最简单。
- 不需要账号系统。
- 不需要数据库。
- 适合 V0 / 早期 V1。

缺点：

- 每次修改都需要改文件、重新部署。
- 对非代码用户不够友好。

### 方案 B：密码保护后台 + 数据库存储

后台在固定网址，例如 `/admin`，登录后可以用按钮修改内容。

内容存到数据库里，例如 Supabase。

优点：

- 更接近用户想要的“自己点按钮更新”。
- 修改内容不一定需要重新部署。
- 可以排序、新增、删除、隐藏。

缺点：

- 需要账号或密码保护。
- 需要数据库。
- 需要多做权限和安全处理。

### 方案 C：第三方内容后台

使用 Notion、Airtable、Sanity、TinaCMS 等现成后台。

优点：

- 后台功能现成。
- 表格式编辑直观。

缺点：

- 视觉和当前主页不一致。
- 可能产生额外账号、成本或维护复杂度。
- 对当前“像主页一样的后台编辑页”目标不一定最合适。

## 当前推荐路线

建议分阶段：

```txt
V0：静态数据写在页面里，先确认视觉和内容结构
V1：把内容抽成独立 JSON / TS 数据文件，方便后续迁移
V1.5：增加 /admin 编辑页和密码保护
V2：如果项目内容变多，再接数据库和更完整权限
```

这样做的理由：

- 不让后台拖慢主页 V1 上线。
- 先把内容结构设计好，后面接后台时不用重做页面。
- 早期用简单方案，等内容真的频繁变化再加数据库。

## 重要设计原则

- 公开主页和后台编辑页应共用同一份内容结构。
- 不要让后台成为复杂产品，先满足自己更新内容。
- 不要把私密内容写进公开数据。
- 后台路径不能代替真正权限，必须有登录或密码保护。
- 删除操作需要确认，避免误删。
- 排序应尽量用按钮或拖拽，不要求用户写数字。
